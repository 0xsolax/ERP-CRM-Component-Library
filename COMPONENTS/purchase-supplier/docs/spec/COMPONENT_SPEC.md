# COMPONENT_SPEC｜purchase-supplier

## 业务边界

本组件负责：

- 供应商档案：编号、名称、简称、地址、联系人、标签、跟进记录。
- 供应商规格对照：产品规格、供应商规格、供应商价格、最小起订量等采购基础信息。
- 待采购申请：订单或库存预警生成采购申请，采购员更换供应商、追加到采购单、撤回申购。
- 采购单：供应商维度采购单、采购明细、产品/半成品列表、跟进、通知供应商、导出、暂存删除。
- 采购退货：采购单退货、退货记录、退货统计和退货详情。
- 库存预警申购：库存预警列表、申购详情、提交申购。

本组件不负责：

- 报价阶段供应商绑定和报价成本决策；报价阶段原则上不强绑定供应商。
- 产品、规格、BOM、图片和供应商规格主数据以外的产品维护。
- 订单生成、订单状态、客户归属和销售权限。
- 仓库入库、库存流水、在途库存和发货。
- 财务付款、应付、对账、利润核算。

依赖组件：

- 基础依赖：`BASE/project-scaffold`、`auth-permission`。
- 建议依赖：完整采购申请/采购单链路建议接入 `order-management`、`product-material`。
- 可选依赖：`customer-management`、`warehouse-delivery`、`finance`、`file-oss`。

## 后端规范

- Controller：区分供应商、待采购、采购单、库存预警；破坏性动作使用 DELETE/POST，不使用 GET。
- Service / Manager：采购申请、采购单生成、退货、通知、撤回必须校验租户、供应商、订单/库存来源、状态和数量。
- DTO / VO：供应商、采购申请、采购单、采购明细、退货、库存预警分别建模。
- 错误处理：供应商不存在、供应商规格缺失、重复生成采购单、数量不足、状态不允许、越权访问必须返回明确错误。
- 事务边界：采购单生成、追加、撤回、退货、入库回写、付款回写必须保证主表、明细、申请来源和操作记录一致。

## 前端规范

- 页面入口：供应商、待采购、已采购、库存预警是当前复杂采购最小页面集合。
- API 封装：采购 API 保持在 `api/admin/purchase/*`，跨模块 API 只作为依赖调用。
- 路由：只挂载 `/purchase/*`，不带入仓库、财务、订单页面。
- 状态管理：采购状态、付款方式、半成品状态、采购操作类型应使用常量。
- 表单和列表：采购申请数量、采购单数量、入库数量、退货数量、付款金额要清晰区分。

## 数据规范

- 简版供应商：`supplier`。
- 复杂供应商：`pur_yt_supplier`、`pur_yt_supplier_follow`、供应商联系人/标签和供应商规格对照。
- 待采购：`pur_yt_apply_purchase`。
- 采购单：`pur_yt_purchase`、`pur_yt_purchase_item`。
- 采购辅助：`pur_yt_purchase_follow`、`pur_yt_purchase_payment`、`pur_yt_store_warning`。
- 状态：采购中、已入库、已发货、暂存，以及半成品确认状态。

## 权限规范

- 菜单权限：供应商列表、待采购列表、已采购列表、库存预警。
- 操作权限：新增/编辑供应商、供应商详情、生成采购单、换供应商、追加采购、撤回申购、采购单退货、通知供应商、导出。
- 数据范围：采购员、部门负责人、老板/全公司视角需要区分供应商、订单来源、客户和采购单可见性。
- 后端强制：不能只依赖前端按钮隐藏；供应商详情、采购单详情、导出、退货、通知供应商必须做后端校验。

## 装配步骤

1. 先确认目标项目只需要供应商 CRUD，还是需要完整采购申请/采购单链路。
2. 先接入 P0 基座与认证权限；如采用复杂采购流，再接入订单和产品物料组件。
3. 设计供应商、采购申请、采购单、采购明细、库存预警、付款和跟进表。
4. 接入供应商列表、详情、新增编辑、联系人、标签、跟进。
5. 接入待采购、生成采购单、换供应商、追加和撤回。
6. 接入采购单列表、详情、退货、跟进、通知和导出。
7. 补齐权限、数据范围、状态前置校验、操作记录和真实账号验收。
