# COMPONENT_SPEC｜order-management

## 业务边界

本组件负责：

- 订单主档：客户、来源平台、来源报价、币种、收货信息、业务员、跟单员、交期、备注。
- 订单明细：子订单、商品项、产品规格、数量、价格、供应商、库存/在途占用、采购数量、入库数量、发货数量。
- 订单状态：暂存、待采购、待入库、待打包、待发货、已发货、已完成、待确认、已关闭。
- 订单动作：新增编辑、审核、设置汇率、删除/关闭、退货、半成品确认、申请采购、确认发货、确认完成、修改发货方式、导出。
- 订单审计：商品项操作记录、退货记录、关闭预览与关闭原因。

本组件不负责：

- 客户主档维护、客户归属和客户数据权限策略。
- 产品、规格、包材、供应商报价和库存主数据维护。
- 采购单全流程、付款、入库、供应商对账。
- 仓库入库、打包、物流包裹、发货单完整实现。
- 财务应收、利润核算、收款流水、对账。

依赖组件：

- 必选：`BASE/project-scaffold`、`auth-permission`、`customer-management`、`product-material`、`quote-management`。
- 可选：`purchase-supplier`、`warehouse-delivery`、`finance`、`file-oss`。

## 后端规范

- Controller：按业务动作拆出订单、采购申请、物流/导出边界；破坏性或状态变更接口使用 POST/DELETE，不使用 GET。
- Service / Manager：写接口必须校验租户、订单归属、客户范围、状态前置条件、子表归属和重复提交。
- DTO / VO：请求对象区分新增编辑、列表查询、退货、发货、关闭、导出；响应对象避免泄漏无权限成本、利润、客户敏感字段。
- 错误处理：订单不存在、无权限、状态不允许、数量不足、重复退货、重复完结、采购申请重复应返回明确业务错误。
- 事务边界：保存订单主从表、申请采购、退货、确认发货、确认完成、关闭订单必须在事务中维护主表、子表、商品项和操作记录一致性。

## 前端规范

- 页面入口：列表、新增、编辑、详情、申请采购是最小复杂订单页面集合。
- API 封装：订单 API 保持在 `api/admin/sales/order.ts`，跨模块 API 只作为依赖调用，不在订单组件内扩展对方维护能力。
- 路由：只挂载 `/sales/order` 及订单子页面，避免带入客户、报价、独立仓历史等其他销售页面。
- 状态管理：订单状态、商品项状态、发货方式、操作类型应使用统一常量，不在页面内重复硬编码。
- 共享依赖：`footer-actions`、`product-selector`、`tagsStore`、`bz-table`、`download/auth/axios` 归前端基座、产品物料或共享组件，不能误收为订单私有能力。
- 表单和列表：订单商品项的数量、价格、库存、在途、采购、入库、发货字段必须清晰区分来源和可编辑性。

## 数据规范

- 主表：简版使用 `orders`；复杂流使用 `sal_yt_order`。
- 子表：简版使用 `order_item`；复杂流使用 `sal_yt_order_sub`、`sal_yt_order_sub_item`。
- 扩展表：复杂流需要半成品确认、操作记录、子订单回款、退货记录和采购申请桥接。
- 枚举/状态：父订单状态、商品项状态、发货方式、退货类型、回款状态必须分别定义。
- 唯一键：订单编号、子订单编号、平台订单号需要租户内唯一策略。
- 逻辑删除：复杂流应继承基座软删除字段，删除动作接入前建议改为关闭/作废优先。

## 权限规范

- 菜单权限：订单列表、订单详情、新增编辑、申请采购、导出、物流导出。
- 操作权限：审核、设置汇率、删除/关闭、退货、半成品确认、确认发货、确认完成、修改发货方式。
- 数据范围：至少按订单客户归属、业务员、跟单员、部门、全公司/老板视角过滤。
- 后端强制：不能只依赖前端按钮隐藏；详情、导出、退货、发货、关闭等必须做服务端校验。

## 装配步骤

1. 先确认目标项目采用简版订单还是复杂订单。
2. 先接入认证权限、客户、产品物料、报价组件。
3. 设计订单 DDL、状态机、编号规则、金额精度和跨模块引用。
4. 接入订单列表、详情、新增编辑、审核和订单明细。
5. 按需接入采购申请、退货、半成品确认、发货、完结、关闭和导出。
6. 补齐后端数据范围、状态前置校验和操作记录。
7. 用真实角色做本人/部门/全公司/老板视角验收。
